Z-Protocol — Technical Report

A post-quantum, zero round-trip transport security protocol — design, implementation, and verification

What is Z-Protocol?

Z-Protocol is a custom-built network security protocol that replaces the traditional TLS handshake with a single UDP packet containing everything needed to establish a quantum-safe encrypted connection — key exchange, authentication, and encrypted data, all in one shot, with zero round trips.

Standard HTTPS/TLS requires at least one round trip before any data can flow. Z-Protocol sends the key exchange, proof-of-work authentication token, and encrypted payload all in the very first packet — this is called 0-RTT (zero round-trip time).

It is also post-quantum secure, meaning it relies on cryptographic algorithms that remain hard to break even with access to a large-scale quantum computer, unlike the classical algorithms (RSA, ECDSA, ECDH) that secure most of today's internet traffic.

Why this approach

TLS 1.3, which secures essentially all HTTPS traffic today, has two structural limitations this project addresses:

1

Quantum exposure: TLS relies on X25519 and RSA for key exchange. Shor's Algorithm, running on a sufficiently powerful quantum computer, can break these in polynomial time — meaning encrypted traffic captured today could be decrypted retroactively once such hardware exists.

2

Handshake latency: TLS 1.3 requires at least one round trip before application data flows. Under packet loss, TCP retransmission compounds this — our measurements show TLS latency growing from ~7ms to ~98ms as packet loss increases from 0% to 10%.

Z-Protocol addresses both simultaneously: quantum-resistant cryptography with zero handshake overhead, built on stateless UDP so packet loss does not trigger retransmission delays.

Why liboqs

Phase 2 — Core Protocol Engine

Building the packet format, key exchange, transport, and encryption

Goal of this phase
Implement the actual Z-Protocol — binary packet format, hybrid key exchange, UDP transport, AES-GCM encryption — and confirm end-to-end encrypted communication.

Packet header design

Design rationale

Every field is positioned to let the server make a drop/continue decision as early as possible. The proof-of-work token is checked before the expensive key decapsulation step, so invalid traffic is rejected before it costs meaningful CPU time.

Header layout (1654 bytes fixed):
┌──────────────────────────────────────────────────┐
│ VERSION      │ 1 byte  │ Protocol version = 0x01 │
│ PACKET TYPE  │ 1 byte  │ 0x01=handshake 0x02=data│
│ SESSION ID   │ 8 bytes │ Random unique per conn   │
│ TIMESTAMP    │ 8 bytes │ Unix time (replay guard) │
│ POW TOKEN    │ 32 bytes│ SHA3-512 proof-of-work   │
│ KEM PUBKEY   │1568bytes│ ML-KEM-1024 public key   │
│ X25519 PUBKEY│ 32 bytes│ Classical hybrid key     │
│ PAYLOAD LEN  │ 4 bytes │ Length of encrypted data │
└──────────────────────────────────────────────────┘
Payload: KEM ciphertext (1568B) + AES-GCM data

Hybrid key exchange

Why combine X25519 and ML-KEM-1024

This is the NIST-recommended approach for transitioning to post-quantum cryptography. If a future quantum attack breaks X25519, ML-KEM-1024 still protects the session. If ML-KEM-1024 is later found to have a mathematical weakness, X25519 still protects it. Two independent mechanisms securing the same connection.

x_shared    = X25519(client_private, server_x_public)
kem_shared  = ML-KEM-1024.Decap(server_kem_private, ciphertext)
combined    = x_shared || kem_shared
session_key = HKDF-SHA256(combined, info="z-protocol-session-key-v1", len=32)

UDP transport layer

Why UDP instead of TCP

TCP carries built-in connection state, handshake, and retransmission — exactly what Z-Protocol is designed to remove. UDP means the server has no per-connection setup: it receives a packet, processes it, replies. This makes 0-RTT possible and keeps latency flat under packet loss, since UDP simply drops lost packets rather than retransmitting and stalling.

AES-256-GCM encryption

Why this cipher specifically

GCM mode provides encryption and authentication together — any tampering with ciphertext causes decryption to fail rather than silently corrupting data. The 256-bit key provides a 128-bit post-quantum security margin, since Grover's algorithm halves the effective strength of symmetric keys against a quantum attacker.

End-to-end test result

A 3294-byte Z-Protocol packet was built by the client. The server received it, independently derived the same session key, and decrypted the message correctly: "Hello from Z-Protocol client - quantum safe!"

Phase 3 — Resilience Layer

Hardening the protocol against denial-of-service, replay, and key compromise scenarios

Goal of this phase
Add the security mechanisms required to make Z-Protocol viable in adversarial network conditions.

SHA3-512 proof-of-work

Why PoW before key decapsulation

ML-KEM-1024 decapsulation costs real CPU time. Without a gate, an attacker can flood the server with fake packets, forcing it to perform expensive key operations on garbage data — a resource exhaustion attack. The client must find a nonce where SHA3-512(nonce + session_id + timestamp) begins with two zero bytes. The server verifies this with a single hash operation before touching the key exchange; invalid proof-of-work causes the packet to be dropped immediately.

Client brute-forces: SHA3-512(nonce || session_id || timestamp)[:2] == 0x0000
Server verifies in O(1): one hash, no brute force needed
Measured solve time on test hardware: 14–95ms at difficulty=2

Double Ratchet forward secrecy

Why rotate keys per message

If an attacker records encrypted traffic and later compromises the session key, forward secrecy prevents that key from decrypting prior messages. Each message uses a key derived by advancing a one-way chain — the same approach used in the Signal messaging protocol.

msg_key_1  = HKDF(chain_key, info="z-protocol-msg-key")
chain_key  = HKDF(chain_key, info="z-protocol-chain-advance")
msg_key_2  = HKDF(chain_key, info="z-protocol-msg-key")
... each message key is independent, derived forward only

Replay attack protection

Why replay protection matters for 0-RTT

Zero-RTT protocols carry a known risk: an attacker can record a client's first packet and resend it later, and a naive server would process it as legitimate. This is mitigated with two layers — a 30-second timestamp window, and a nonce registry that tracks every proof-of-work nonce already seen.

Test caseExpectedObserved
Fresh packet, first timePassPass
Same packet replayedDropDropped
Fresh packet, new noncePassPass
Packet with 60s old timestampDropDropped

Session state design

What "stateless" means here

Z-Protocol is stateless at the transport level — no TCP handshake, no connection tracking. Forward secrecy does require remembering ratchet state, so the server keeps a minimal session record: ratchet state, creation time, last-seen time. Sessions expire and are evicted automatically after 3600 seconds.

Live test result

Server output confirmed all five checks in sequence on a real packet: timestamp valid, proof-of-work verified, replay check passed, session key derived, message decrypted.

Goal of this phase

Network stress testing

Why simulate packet loss

Real networks are imperfect. A protocol that performs well only on a clean loopback connection is not a meaningful contribution. The Linux kernel's tc-netem tool introduces controlled artificial packet loss on the loopback interface, allowing measurement of both protocols under realistic degraded conditions without needing physically degraded hardware.

sudo tc qdisc add dev lo root netem loss 5%
# All loopback traffic now drops 5% of packets randomly
# Both protocols benchmarked under identical conditions
sudo tc qdisc del dev lo root   # cleared afterward

Manual Proxy Configuration

How the browser demonstration is wired up, and why this configuration was chosen

What is being demonstrated
Real Firefox browser traffic is routed through the Z-Protocol tunnel instead of going directly to the internet — proving the protocol functions as an actual usable network layer, not only a benchmark script.

Architecture

1

Firefox is configured with a manual proxy pointing to 127.0.0.1:9999. Every HTTP request the browser makes is sent to this address instead of the open internet.

2

A local process listens on port 9999. It wraps each incoming browser request inside a Z-Protocol packet — generating the hybrid key exchange, attaching a proof-of-work token, and encrypting the HTTP data with AES-256-GCM.

3

The completed Z-Protocol packet is sent as a single UDP datagram to port 9000 — no TCP connection, no handshake, no persistent state.

4

The server process receives the UDP packet, decapsulates the key exchange to recover the session key, decrypts the HTTP request, and forwards it to a local web server on port 8080.

5

The web server responds normally. The server process encrypts the response with the same session key and sends it back over UDP.

6

The client process decrypts the response and hands it back to Firefox as a standard HTTP response — the browser renders the page with no awareness of the underlying protocol.

Firefox → [HTTP request] → client proxy (port 9999)
              ↓ wrap in Z-Protocol packet
              ↓ ML-KEM-1024 encapsulate + AES-256-GCM encrypt
              ↓ single UDP datagram to port 9000
server proxy → verify proof-of-work → decapsulate key exchange
              → decrypt → forward to local web server (port 8080)
              → encrypt response → UDP back to client
client proxy → decrypt → hand back to Firefox

Why a manual proxy configuration, specifically

Reasoning behind this choice

A transparent proxy would require kernel-level traffic interception (iptables redirect rules), which adds complexity and obscures exactly what is happening to the traffic. A manual proxy is explicit: the browser is told directly where to send its requests, the routing is fully visible in Firefox's own network settings, and the demonstration becomes easy to verify, stop, and restart on demand. It also makes the kill-switch test possible — stopping the client proxy process immediately and visibly breaks the connection, because there is no fallback path for the browser to use.

Why three separate ports

Separation of concerns

Port 9999 (client side) and port 9000 (server side) form the Z-Protocol tunnel itself. Port 8080 is an entirely separate, standard, unencrypted HTTP server. This separation is deliberate — it proves the tunnel is carrying real traffic to a real backend, rather than the proxy fabricating a response internally. The web server has no knowledge that Z-Protocol exists; it simply receives a normal HTTP request and replies normally.

Real-World Deployment Considerations

How this would function outside a single loopback machine, across routers, switches, and ISP infrastructure

Important framing
Everything demonstrated so far runs on one machine over the loopback interface (127.0.0.1), which has no real network hardware in the path. Real deployment introduces hardware and infrastructure factors that do not exist in a loopback test. This section addresses those honestly.

What changes outside a single machine

Routers and NAT

Home and enterprise routers perform Network Address Translation. A UDP-based protocol like Z-Protocol needs the router's NAT table to correctly map outbound requests to inbound responses. Most consumer routers handle UDP NAT mapping fine, but mappings can time out faster for UDP than TCP — typically 30 to 300 seconds of inactivity before the mapping is dropped, compared to several hours for established TCP connections.

Firewalls

Many corporate and ISP-level firewalls are configured to allow TCP port 443 (HTTPS) by default but may block or rate-limit unfamiliar UDP traffic on non-standard ports, since UDP is more commonly associated with abuse (DDoS amplification, scanning). Z-Protocol on raw UDP port 9000 would likely be blocked on many restrictive networks unless explicitly allowed — this is a genuine deployment obstacle, not a protocol design flaw.

Switches

Layer 2 switches forward frames based on MAC address and generally do not interfere with UDP traffic the way a firewall or NAT device might. Switches are largely transparent to Z-Protocol — they are not a significant obstacle, unlike routers and firewalls.

Load balancers

If Z-Protocol were deployed at scale behind a load balancer, the load balancer would need UDP support and would need to either terminate the protocol itself or pass datagrams through unmodified to a consistent backend. Most commercial load balancers (such as AWS NLB) support UDP, but configuration would need explicit attention — this is not automatic the way TCP load balancing is.

MTU and fragmentation

The 3294-byte first packet exceeds the standard 1500-byte Ethernet MTU on real networks (loopback has no such limit, which is why this was not visible in testing). On a real network this packet would fragment into 3 IP fragments. Fragmented UDP is more likely to be dropped by security-conscious routers and firewalls, which is documented as a known limitation requiring future work (key compression or Path MTU Discovery).

ISP and carrier-grade NAT

Mobile carriers and some ISPs deploy carrier-grade NAT, which can be particularly aggressive about closing UDP mappings quickly to conserve resources across many subscribers. This would affect session longevity in real deployment more than it does on a fixed home connection.

What this means in practice

The cryptographic core of Z-Protocol — the hybrid key exchange, the encryption, the proof-of-work filter, the forward secrecy — does not depend on any of the network hardware listed above and would function identically wherever UDP packets are allowed to pass. What changes in a real deployment is reachability: whether the UDP packets are permitted through in the first place by the intermediate hardware on the path between client and server.

This is the same challenge that QUIC (Google's UDP-based transport, now used by HTTP/3) faced during its real-world rollout — some networks blocked or throttled UDP traffic, requiring fallback logic to retry over TCP/TLS when UDP was unavailable. A production deployment of Z-Protocol would likely need the same kind of fallback path for networks where UDP port 9000 is blocked.

What would be needed for production deployment

RequirementReason
UDP keep-alive or shorter session refreshTo survive NAT table timeouts on routers and carrier-grade NAT
TCP/TLS fallback pathFor networks where UDP traffic is blocked or filtered by firewalls
Path MTU Discovery or key compressionTo avoid fragmentation of the 3294-byte first packet on real networks
Explicit firewall rules for UDP port 9000Required on any restrictive enterprise or institutional network
UDP-aware load balancing at scaleIf deployed across multiple servers rather than a single host

This is presented as an honest assessment, not a weakness to hide. The current implementation is a working research prototype validated on loopback and proven functionally correct end to end. Real-world rollout would require the additions above — the same maturation path every new transport protocol (including QUIC and HTTP/3) has gone through before widespread adoption.

Quantum resistance — what can and cannot be claimed

Confirmed algorithm
$ python3 verify_kem.py
[+] Engine active: ML-KEM-1024
[+] Public key size: 1568 bytes
[+] Ciphertext size: 1568 bytes
[+] ML-KEM-1024 working correctly!

The 1568-byte key and ciphertext sizes exactly match the published NIST FIPS 203 specification for ML-KEM-1024, confirming the real standardized algorithm is in use, not a placeholder.

Honest assessment

No quantum computer capable of threatening ML-KEM-1024 currently exists, so this cannot be empirically tested in this lab. What can be demonstrated is that the packet uses ML-KEM-1024, a NIST-standardized algorithm (FIPS 203) whose security rests on the Module Learning With Errors lattice problem. Unlike RSA and elliptic curve cryptography used in classical TLS, no efficient quantum algorithm is currently known against this class of problem — this is the reasoning behind NIST's selection of it as the post-quantum standard after years of public cryptanalysis. The contribution here is not new cryptography — it is correctly implementing this already-vetted algorithm inside a novel zero-RTT transport architecture, and demonstrating that architecture is measurably faster than TLS 1.3 while carrying this protection.

What is happening on each request

Every request from the browser is intercepted by the client proxy on port 9999, wrapped inside a Z-Protocol packet containing a fresh post-quantum key exchange, a proof-of-work token, and the encrypted HTTP data — all as a single UDP packet sent to port 9000. The server verifies the proof-of-work, decapsulates the key exchange, decrypts the request, fetches the page, encrypts the response, and sends it back. The browser never touches the network directly. Each number on this dashboard represents one of those encrypted exchanges.

What each session key represents

Every row in the request log shows a unique session key prefix, derived fresh for that single request using both ML-KEM-1024 and X25519 combined through HKDF. Each key is used once and then discarded — this is the forward secrecy property in action, visible directly in the log.
